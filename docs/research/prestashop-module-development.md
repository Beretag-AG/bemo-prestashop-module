# PrestaShop module-development contract for BEMO-359

Verified against first-party PrestaShop documentation and source on **2026-08-08**. The implementation target is one installable `bemoliveshopping` artifact for PrestaShop **1.7.6 through 8.x**. PrestaShop 8 documentation is now marked outdated in favor of PrestaShop 9, so the versioned 1.7.6.9 and 8.2.x source links below are the authority where lifecycle or multistore behavior matters.

That target is valid for a direct/private distribution, but it is **not a current PrestaShop Marketplace target**. Marketplace standards require new products to support the latest PrestaShop major, currently PrestaShop 9, and since February 1, 2026 updates to existing products are rejected when they do not. An 8.x ceiling must therefore be described as the BEMO-359 runtime scope, not as Marketplace readiness. [Current Marketplace technical standards](https://docs.cloud.prestashop.com/2-technical-development-standards/#compatibility-with-prestashop-versions)

## Decisions to carry into the implementation

[Module tutorial](https://devdocs.prestashop-project.org/8/modules/creation/tutorial/#tutorial-creating-your-first-module) |

## Installable module and ZIP layout

The archive must contain a top-level module subdirectory, not loose files. The module directory and main PHP file must share the technical name. `config.xml`, `logo.png`, `src/`, `views/`, `vendor/`, and `upgrade/` are conventional or optional according to the module's needs; `config.xml` is a cached copy of module metadata and including it lets upgrade scripts be discovered immediately after a ZIP download. [Module file structure](https://devdocs.prestashop-project.org/8/modules/creation/module-file-structure/)

For current Marketplace validation, the root also needs `.htaccess`, every shipped directory needs an `index.php`, and every PHP file must include the `_PS_VERSION_` context guard. Marketplace submissions additionally require a `module_key` generated by the seller account and English PDF documentation. These are Marketplace packaging requirements, not prerequisites for PrestaShop itself to load a privately distributed module. [Current Marketplace technical standards](https://docs.cloud.prestashop.com/2-technical-development-standards/#required-module-structure), [current submission checklist](https://docs.cloud.prestashop.com/5-submission-and-validation-process/#mandatory-pre-submission-checklist)

The BEMO artifact should therefore be:

```text
bemoliveshopping.zip
└── bemoliveshopping/
    ├── bemoliveshopping.php
    ├── config.xml
    ├── index.php
    ├── .htaccess             # mandatory for Marketplace distribution
    ├── LICENSE.md
    ├── composer.json
    ├── config/
    ├── src/
    ├── views/                 # only if templates/assets are used
    ├── upgrade/               # once a later release needs migrations
    ├── docs/                  # merchant documentation, if distributed
    └── logo.png               # recommended 140×140 PNG
```

For Marketplace submission, the current checklist says the ZIP must contain all necessary files and use the exact registered technical name. The automated Validator is the first validation stage. The older technical-tools page adds the still-useful archive detail that the ZIP/folder/main-file names match and the ZIP name omit a version suffix, but it is historical guidance and must not override the current Marketplace standards. [Current submission checklist](https://docs.cloud.prestashop.com/5-submission-and-validation-process/#mandatory-pre-submission-checklist), [technical tools and packaging](https://devdocs.prestashop-project.org/1.7/modules/sell/technical-tools/)

If runtime Composer dependencies are introduced, run an optimized production install/dump before packaging, include `vendor/`, set `config.prepend-autoloader` to `false`, and exclude development dependencies from the artifact. A merchant must not need to run Composer after uploading the ZIP. [Composer packaging guidance](https://devdocs.prestashop-project.org/8/modules/concepts/composer/)

## Main class, install, uninstall, and upgrades

The main file must guard direct execution with `defined('_PS_VERSION_')`, declare a PascalCase class matching the module name, and extend `Module`. Set `$this->name` before `parent::__construct()` and call the parent before using translation methods. For Marketplace packaging, apply the same guard to **every** PHP file. [Module tutorial](https://devdocs.prestashop-project.org/8/modules/creation/tutorial/#the-constant-test), [current Marketplace technical standards](https://docs.cloud.prestashop.com/2-technical-development-standards/#php-context-guard)

`install()` and `uninstall()` return booleans. Installation must include `parent::install()` and every required setup operation; any false result aborts installation. Uninstallation should reverse module-owned state and call `parent::uninstall()`. PrestaShop's own example deletes the configuration it created during installation. [Install/uninstall guide](https://devdocs.prestashop-project.org/8/modules/creation/tutorial/#building-the-install-and-uninstall-methods)

For BEMO, keep installation side effects small and retryable:

1. `install()` calls `parent::install()` and creates only the module-owned table/configuration needed to render the configuration page.
2. Do **not** enable Webservice or mint credentials during install; those actions should occur behind the explicit provisioning control because PrestaShop ships Webservice disabled by default. [Webservice enablement](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#enable-the-webservice)
3. If provisioning creates an account but a later permission or persistence step fails, delete that newly created account before returning the error. This compensation follows from PrestaShop's boolean lifecycle contract and prevents a retry from leaking usable credentials. [Install contract](https://devdocs.prestashop-project.org/8/modules/creation/tutorial/#the-install-method), [WebserviceKey deletion in 8.2.x](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/webservice/WebserviceKey.php#L87-L116)
4. `uninstall()` must enumerate and delete **all** module-owned Webservice account IDs before dropping the module table, remove module configuration, then call `parent::uninstall()`. Do not delete keys discovered only by description or delete a merchant-created key. PrestaShop recommends removing all module-owned configuration/entities on uninstall. [Module good practices](https://devdocs.prestashop-project.org/8/modules/creation/good-practices/), [install/uninstall guide](https://devdocs.prestashop-project.org/8/modules/creation/tutorial/#the-uninstall-method)
5. Do not blindly disable `PS_WEBSERVICE` on uninstall: PrestaShop stores the switch in Configuration and other integrations may rely on it. Leaving a shared switch enabled is safer than revoking functionality the module does not exclusively own. [Webservice enablement](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#enable-the-webservice)

When a later release changes data or hooks, set the new module version and add `upgrade/upgrade-x.y.z.php` containing `upgrade_module_x_y_z($module)`. PrestaShop executes eligible scripts sequentially from the first version newer than the installed one; each script must return success. [Module upgrade guide](https://devdocs.prestashop-project.org/8/modules/creation/enabling-auto-update/)

## Configuration page contract

`getContent()` is both the configuration-page renderer and submission entry point. PrestaShop shows the Configure button only when this method exists. The documented legacy pattern uses `Tools::isSubmit()`, `Tools::getValue()`, explicit validation, `displayError()`/`displayConfirmation()`, and a `HelperForm`. [Legacy configuration-page guide](https://devdocs.prestashop-project.org/8/modules/creation/adding-configuration-page/)

For the BEMO page:

- Use a module-specific submit action and `Tools::getAdminTokenLite('AdminModules')` through `HelperForm`; validate the BEMO endpoint before persistence and render success/failure visibly. This follows the documented `HelperForm` submission pattern and PrestaShop's rule that forms validate input and show a confirmation or error. [Configuration-page guide](https://devdocs.prestashop-project.org/8/modules/creation/adding-configuration-page/), [module good practices](https://devdocs.prestashop-project.org/8/modules/creation/good-practices/)
- Keep “Save settings” separate from “Enable and provision Webservice access.” The official docs say Webservice is disabled by default and creating a key grants API access, so provisioning merits an explicit confirmation. [Webservice access guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/)
- Show connection state and the selected shop context, but never render or log the Webservice key, pairing token, webhook secret, or buy-link secret after provisioning. The Marketplace checklist requires external calls and AJAX endpoints to use unique secured tokens and forbids debug output in release artifacts. [Marketplace security checklist](https://devdocs.prestashop-project.org/1.7/modules/sell/techvalidation-checklist/#calls-from-external-services-are-secured)

## `WebserviceKey`: creation, permissions, and multistore cleanup

### Creation

PrestaShop's documented programmatic flow is `new WebserviceKey()`, assign `key`, save/add the model, then call `WebserviceKey::setPermissionForAccount($id, $permissions)`. The model requires a 32-character key and rejects duplicates in both 1.7.6.9 and 8.2.x. [Webservice access guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#programatically), [1.7.6.9 `WebserviceKey`](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/webservice/WebserviceKey.php#L38-L62), [8.2.x `WebserviceKey`](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/webservice/WebserviceKey.php#L38-L86)

Use `Tools::passwdGen(32)` and fail closed if it returns `false`. In 1.7.6.9 it builds the value from OpenSSL-generated bytes; in 8.2.x the same public helper delegates to PrestaShop's OpenSSL-backed `PasswordGenerator`, so it is the stable cross-version helper. [1.7.6.9 `Tools::passwdGen`](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/Tools.php#L82-L147), [8.2.x `Tools::passwdGen`](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/Tools.php#L106-L135)

Set `active`, a BEMO-specific description, and `$account->id_shop_list` **before** `add()`. `ObjectModel::add()` uses `id_shop_list` instead of the current context when it is non-empty and inserts the corresponding `<table>_shop` rows in both target versions. [1.7.6.9 `ObjectModel::add`](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/ObjectModel.php#L542-L575), [8.2.x `ObjectModel::add`](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/ObjectModel.php#L608-L640)

### Least privilege

Permissions are keyed by Webservice resource and then HTTP method. PrestaShop tells implementers to select only rights needed for that key and not grant all rights on all resources. `setPermissionForAccount()` accepts only known resources and method names; 1.7.6 supports `GET`, `PUT`, `POST`, `DELETE`, and `HEAD`, while 8.2 also accepts `PATCH`. [Webservice permissions guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#create-an-access-key), [1.7.6.9 permission implementation](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/webservice/WebserviceKey.php#L111-L143), [8.2.x permission implementation](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/webservice/WebserviceKey.php#L182-L214)

The BEMO integration should therefore grant only `GET` and `HEAD`, and only for resources proved necessary by the BEMO server call graph. The currently proposed catalog set (`products`, `combinations`, `stock_availables`, `specific_prices`, `cart_rules`, `images`, `languages`, `currencies`, `shops`, `taxes`, `tax_rules`) must be reduced whenever an endpoint is not actually called; do not add `POST`, `PUT`, `PATCH`, or `DELETE` “for convenience.” This is the direct least-privilege application of PrestaShop's permission guidance. [Webservice permissions guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#create-an-access-key)

Before persisting credentials, verify every requested resource exists in `WebserviceRequest::getResources()` on that shop and reject an empty or partially unknown map. PrestaShop identifies `getResources()` as the authoritative list, while `setPermissionForAccount()` silently filters unknown resource/method entries. [Programmatic permissions guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#programatically), [1.7.6.9 filter logic](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/webservice/WebserviceKey.php#L111-L143)

### Multistore and deletion

Webservice keys have explicit shop associations in multistore mode; an API key can access only associated shops, and a newly created shop will not automatically be available to an existing key until its association is updated. [Webservice access guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/creating-access/#via-the-user-interface), [multishop Webservice guide](https://devdocs.prestashop-project.org/8/webservice/tutorials/advanced-use/manage-multishop/)

Provision one account per selected shop unless BEMO intentionally supports one credential shared across several shops. In the per-shop design, assign exactly `array($shopId)` to `id_shop_list` before `add()` and store the resulting account ID with that shop's module record. This follows the core's explicit association mechanism and keeps credentials revocable per shop. [1.7.6.9 `ObjectModel::add`](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/ObjectModel.php#L542-L575), [8.2.x `ObjectModel::add`](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/ObjectModel.php#L608-L640)

Deletion is context-sensitive. `ObjectModel::delete()` removes only associations in `id_shop_list`, or the current shop-context list when `id_shop_list` is empty; it deletes the base account row only after no multishop entries remain. `WebserviceKey::delete()` then removes its permission rows. This behavior is materially the same in 1.7.6.9 and 8.2.x. [1.7.6.9 `ObjectModel::delete`](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/ObjectModel.php#L828-L870), [8.2.x `ObjectModel::delete`](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/ObjectModel.php#L901-L947), [1.7.6.9 `WebserviceKey::delete`](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/webservice/WebserviceKey.php#L67-L76)

Consequently, BEMO uninstall must not fetch only the current shop's account and then drop the table. It must first enumerate every module-owned account ID, load each key, set `id_shop_list` to all its actual association rows (or otherwise delete all of those rows), call `$account->delete()`, and abort the table drop if any deletion fails. That is the only way to avoid orphaning accounts/permissions when the module was provisioned in multiple shops. [1.7.6.9 deletion behavior](https://github.com/PrestaShop/PrestaShop/blob/1.7.6.9/classes/ObjectModel.php#L828-L870), [8.2.x deletion behavior](https://github.com/PrestaShop/PrestaShop/blob/8.2.x/classes/ObjectModel.php#L901-L947)

## PrestaShop and PHP compatibility

PrestaShop 1.7.6 officially supports PHP **5.6 through 7.2**, and not PHP 7.3. [PrestaShop project announcement](https://build.prestashop-project.org/news/2019/announcing-end-of-support-for-obsolete-php-versions/#prestashop-is-directly-affected-by-this-change-but-how-exactly)

PrestaShop 8.0–8.2 requires at least PHP **7.2.5**, supports 7.2–8.1, recommends 8.1, and does not support PHP 8.2+. [PrestaShop 8 system requirements](https://devdocs.prestashop-project.org/8/basics/installation/system-requirements/#php-compatibility-chart), [PrestaShop 8.0 changes](https://devdocs.prestashop-project.org/8/modules/core-updates/8.0/#php-support)

There are therefore two honest support policies:

1. **Full target-version coverage:** keep runtime syntax and dependencies compatible with PHP 5.6 through 8.1, so every officially valid 1.7.6 and 8.x installation can load the artifact.
2. **BEMO's current modern floor:** require PHP `>=7.2.5 <8.2`. This covers the runtime overlap used by PrestaShop 8 and many 1.7.6 shops, but it does **not** support 1.7.6 installations still running PHP 5.6–7.1. The configuration/README and an early `install()` guard must say so instead of relying only on `composer.json`, because the uploaded release is self-contained and merchants do not run Composer. The bounds derive from the two official compatibility ranges above. [PrestaShop 1.7.6 PHP range](https://build.prestashop-project.org/news/2019/announcing-end-of-support-for-obsolete-php-versions/#prestashop-is-directly-affected-by-this-change-but-how-exactly), [PrestaShop 8 PHP range](https://devdocs.prestashop-project.org/8/basics/installation/system-requirements/#php-compatibility-chart)

Whichever policy is selected, test the same artifact at the endpoints of its declared matrix. PrestaShop recommends matching the platform's supported PHP range, avoiding syntax newer than the minimum, and accounting for removals/deprecations at the maximum. [Migration guidance for solutions targeting PrestaShop 8](https://build.prestashop-project.org/news/2022/migrate-your-solutions-from-17-to-80/#php-80-and-81)

## Validator, package, and license release gate

PrestaShop's live Validator requires a PrestaShop seller-account sign-in and accepts a module/theme upload for automated checks. Automated validation is the first Marketplace review stage and does not replace the later manual technical and product review. [PrestaShop Validator](https://validator.prestashop.com/), [submission and validation process](https://docs.cloud.prestashop.com/5-submission-and-validation-process/#validation-process)

Before release:

- Build `bemoliveshopping.zip` with exactly one top-level `bemoliveshopping/` module and no version in the ZIP filename. Use the exact technical name registered in the seller account. [Current submission checklist](https://docs.cloud.prestashop.com/5-submission-and-validation-process/#mandatory-pre-submission-checklist), [technical tools and packaging](https://devdocs.prestashop-project.org/1.7/modules/sell/technical-tools/#your-file-and-the-permanent-name-of-your-module)
- Keep the artifact self-sufficient: include runtime code/assets/dependencies and do not download required code or assets after installation. [Marketplace validation checklist](https://devdocs.prestashop-project.org/1.7/modules/sell/techvalidation-checklist/#module-does-not-rely-on-external-assets)
- Include a root `.htaccess`, `index.php` in every shipped directory, and the `_PS_VERSION_` guard in every PHP file. Remove tests, logs, generated files, commented-out code, and debug statements. [Current Marketplace technical standards](https://docs.cloud.prestashop.com/2-technical-development-standards/#security-files-and-directory-protection)
- Populate the seller-issued `module_key` and include user documentation as an English PDF. The research notes themselves need not ship. [Current submission checklist](https://docs.cloud.prestashop.com/5-submission-and-validation-process/#mandatory-pre-submission-checklist)
- Prefix tables, configuration keys, and global classes with the module name; create module-owned tables rather than altering PrestaShop core tables. [Marketplace validation checklist](https://devdocs.prestashop-project.org/1.7/modules/sell/techvalidation-checklist/#core-tables-are-untouched)
- Run the module under PrestaShop debug mode with zero PHP notices, warnings, deprecations, or errors before Validator submission. [Current Marketplace technical standards](https://docs.cloud.prestashop.com/2-technical-development-standards/#code-quality-and-debugging)
- Keep the module's AFL-3.0 declaration, license text, and source headers consistent, and audit bundled component licenses/attributions for AFL compatibility. [Submitting an add-on](https://helpcenter-partners.prestashop.com/hc/en-us/articles/19059375832466-Submitting-my-addon), [Marketplace legal and compliance](https://docs.cloud.prestashop.com/7-legal-and-compliance/#third-party-library-attribution)
- Do not submit the present 1.7.6–8.x-only artifact to the Marketplace. First add and verify PrestaShop 9 compatibility, then upload the final artifact to the official Validator and resolve structural/security errors before submission. [Current Marketplace technical standards](https://docs.cloud.prestashop.com/2-technical-development-standards/#compatibility-with-prestashop-versions), [live Validator](https://validator.prestashop.com/)

## Minimal acceptance matrix

The declared compatibility is not credible until the **same ZIP** is exercised on at least PrestaShop 1.7.6.9/PHP 7.2 and PrestaShop 8.2.x/PHP 8.1, plus PHP 5.6 if the full-coverage policy is chosen. Those versions are the oldest target, newest 8.x line documented by the current 8 requirements, and the supported runtime edges described above. [PrestaShop 1.7.6 PHP range](https://build.prestashop-project.org/news/2019/announcing-end-of-support-for-obsolete-php-versions/#prestashop-is-directly-affected-by-this-change-but-how-exactly), [PrestaShop 8 PHP matrix](https://devdocs.prestashop-project.org/8/basics/installation/system-requirements/#php-compatibility-chart)

For each matrix entry, verify: ZIP upload; install; configuration rendering; endpoint validation; explicit Webservice provisioning; 32-character account creation; exact GET/HEAD permissions; correct shop association; failed-provision compensation; reinstall/idempotency; upgrade-script execution once one exists; and uninstall removing every module-owned account, permission, association, and table while leaving unrelated Webservice accounts and the shared Webservice switch intact. These checks directly exercise the lifecycle, configuration, permission, and multistore contracts cited above.
